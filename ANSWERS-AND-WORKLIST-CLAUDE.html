Three arguments for this over what is specified

  1. Root arity, not depth, is what confuses people. Two entries with obvious roles beats nine flat ones. No item moves more than one level; library/items/x → sources/items/x. Every content.file path in the records needs one prefix rewrite, which is a script, not a project.
  2. Rename library/ → sources/. The repo is source-materials; the folder should say the same word. Three different meanings of "library" across your stack is one too many.
  3. A flat items/ is not browsable, and pretending otherwise is the trap. Three hundred folders named bohr-daniel-8-2019 is a database with a file explorer bolted on. You asked to open one folder and find the studies — that requires grouping, and grouping by topic would break "store each item once," which is the one rule in your design worth protecting. The resolution is a generated browse layer: sources/BROWSE.html, rebuilt from the registry alongside SQLite, grouping by speaker, topic, passage, and authority class, every entry linking into the single physical item. Your design already produces indexes/ — it just files them in the machine folder and points them at machines. Point one of them at you, and put it where you look.

The rule underneath this

Physical storage optimises for one copy. Human browsing optimises for many paths in. Those are different jobs and folders can only do the first. Every time you feel like reorganising a folder tree to make it browsable, the real answer is a generated index. Same rule that applies to the CDSJ reference tree.

2Killing the read/write churn — globally

You framed this as a 120 KB problem. It is not a size problem, it is a method problem, and my own §5 edge 4 in the plan implied the bad method. Correcting it:

Appending to a file does not require reading the file.

The churn happens because agents do read whole file → hold it in context → write whole file back. On a 120 KB stem file that is ~30 K tokens in and ~30 K out for a 400-token addition. An OS-level append costs the new text and nothing else, regardless of how big the file already is. A 2 MB file appends for the same price as an empty one.

Four rules. Put them in WORKSPACE.md once; they apply to every request, every agent, every file type.

#RuleInstead ofCost
1 Append with the shell, never by rewriting.
Add-Content -Path f.md -Value $block (PowerShell) · cat >> f.md <<'EOF' (bash)		 Read → edit → Write whole file New text only. O(1) in file size.
2 Read by range, never whole-file.
Select-String -Pattern 'SELECTED:BEGIN' -Context 0,40 · sed -n '1,40p' · rg -n to locate, then slice		 Loading 120 KB to read a 40-line fence ~1–2% of the file.
3 Move data with the OS, never through the model. Archiving old runs is Get-Content -Tail piped to append + truncate — the agent never holds the moved text. Re-typing 80 KB of old runs into the archive file ≈0 tokens for any volume.
4 Edit in place with a pattern, never a paste. sed -i / a short read-modify-write script the agent writes but does not read the data through. Reproducing a file's contents from earlier tool output (which may be truncated — a correctness bug, not just a cost one) The pattern only.

Tool caveat, stated honestly: Claude Code's Edit tool requires a prior Read of the file by design, so inside that harness rule 1 means "use the shell, not Edit" for appends. Grok and Codex have no such constraint. This is exactly why the rule belongs in WORKSPACE.md as a contract rather than in one agent's config.

Then: does SQLite help?

Yes — for the source library

It is already specified and, as far as I can tell, unbuilt: "database/sources.sqlite3 is rebuilt deterministically… FTS5 content" with a hard rule never to hand-edit it. That is the correct design and it directly answers your question — an agent asking "which approved sources cover Daniel 8:14" should run one query, not open thirty record.yaml files. Build it and make querying it mandatory before any record is opened. The dead scripts/query_sources.py pointer in source-governance.md is the stub where this was meant to land.

No — for stem / run files

You read those. You mark winners with a trailing ~ by hand. Putting them in SQLite means you need a viewer to do what Notepad does today, and the ~ workflow — which works — dies. It would also make agent writes more expensive, not less, because every read comes back through the model as rows instead of as a range you skipped. Markdown plus rules 1–3 is already O(1). There is nothing left for a database to win.

If run logs ever do need machine querying, the cheap step is stem.runs.jsonl — one line appended per run, greppable, still O(1) — not a database. I would not build it until something actually needs to query runs, which nothing does today.

3HTML vs markdown — what it really costs

Measured on your own files, markup overhead over the same prose:

1.34×CLAUDE-REASONING-CHECK
1.58×STACK-HARDENING-IDEAS
1.77×STACK-ROBUSTNESS-PLAN
1.50×HARDENING-PLAN (mine)

Raw bytes over extracted prose. Tokens run somewhat worse than bytes because tags, class names and hex colours fragment badly, so call it 1.5–2× tokens for the same content when an agent reads it. Roughly half of that is the one-time <style> block, which is why the small file shows the best ratio and a long document amortises it.

But the ratio is the wrong thing to optimise. The question is who reads it.

A plan or report is written once by an agent and read many times by you. Your eyes cost nothing. If no agent ever loads it again, its format is free — 1.5× of zero is zero. A skill reference is the opposite: written rarely, loaded by an agent on every matching request, forever.

The rule

  • Human-facing, write-once — plans, reports, reviews, browse indexes, runbooks → HTML. Keep doing exactly what you are doing.
  • Agent-facing, read-often — SKILL.md, references, WORKSPACE.md, CATALOG.md, schemas, load maps → markdown / YAML. Converting these to HTML would tax every request forever.
  • Never both. Two formats of the same content is the twelve-homes problem again, and it is worse than either format alone.

One consequence worth naming: an HTML plan is a terminal document. When an agent needs to act on it, the actionable parts must be restated in the agent-facing files — which is precisely what the work list below does. Do not ask agents to work from the HTML.
